# FloodSafe Nepal — IoT Assignment 3

**Current stage: project skeleton, Python virtual sensor simulator, SQLite local buffer, MQTT/ThingsBoard synchronization, per-node routing to three ThingsBoard devices, and verified ThingsBoard dashboard/rule-engine configuration (Stage 4).**

FloodSafe Nepal is a post-flood water-quality monitoring and decision-support
prototype for the Internet of Things (ITS67404) Assignment 3. Python simulates
ESP32-style monitoring nodes that report five water indicators from three water
points in Kathmandu Valley.

> **Important limitation:** this is an academic prototype, not a laboratory
> water-safety certification system. The readings are generated by a model.
> The coordinates are demonstration coordinates, not verified deployment
> locations and not a claim that equipment is installed there.

## What is included today

- Project folder skeleton and documentation.
- `config/nodes.json` with exactly three simulated nodes and the simulation
  settings.
- A standard-library-only Python simulator with two scenarios: `normal` and
  `flood`.
- JSON Lines output on screen and, optionally, to a file in `output/`.
- A SQLite local buffer (`src/database.py`) that stores readings with
  `sent = 0` until they are transmitted.
- MQTT over TLS publishing to ThingsBoard (`src/mqtt_client.py`) and a one-shot
  synchronization manager (`src/sync_manager.py`).
- Per-node routing: each virtual node uses its own device token and connects to
  its own ThingsBoard device.
- Verified ThingsBoard configuration under `thingsboard/`: sanitised real
  dashboard and operational-state rule-chain exports, alarm-rule reference,
  build sheet and verification checklist.
- Automated tests for the database, MQTT/sync using mocks, and the committed
  cloud configuration files in `tests/`.

## What is NOT included yet

The committed dashboard and rule-chain JSON are **sanitised real exports from a
verified ThingsBoard 4.4.1 tenant**, not invented templates. They were imported,
linked and tested with telemetry in that tenant. If you use a different account,
you must still create/provision the devices, set tokens, import/link the exports
and verify them there before claiming they are live. Device inactivity timeout
is still unset because the assignment gives no value. Performance measurement
(latency, delivery ratio, alarm delay, flush throughput, recovery time and data
loss) is not yet implemented. The sync command is a single controlled run —
there is no endless retry loop.

Some assignment values are genuinely unspecified: numeric thresholds and
persistence counts for the four operational states, the "sustained" duration
for `flow_lpm == 0`, and the device inactivity timeout. These are flagged as
clarification items rather than invented. See `thingsboard/README.md`.

evenly across the three nodes in round-robin order, so each node receives
roughly `--count / 3` readings.

### Normal scenario

Windows (PowerShell):

```powershell

```

macOS / Linux:

```bash

```

### Flood scenario

Windows (PowerShell):

```powershell
python -m src.main --scenario flood --count 12
```

macOS / Linux:

```bash
python3 -m src.main --scenario flood --count 12
```

The flood scenario uses one shared contamination severity for all three nodes.
Severity rises quickly, holds at a peak, then washes out slowly. Turbidity,
pH, TDS and flow all respond to that same severity, so the readings describe
one related event instead of independent random numbers.

To force one exact operational state and its ThingsBoard alarms for a screenshot,
use the deterministic publisher described in
[`thingsboard/operational_states.md`](thingsboard/operational_states.md). The
simulator generates readings; the linked rule chain derives `operational_state`.

## SQLite local buffer

### What SQLite is doing in our project

SQLite is a small database built into Python (`sqlite3`), so no installation or
server is needed. It acts as the **local storage** for our virtual node. Every
reading generated with `--save-db` is written to `data/floodsafe.db` before any
future transmission attempt. This is the first half of *store-and-forward*:
**store now, forward later**.

The table is named `sensor_readings`. It stores the same 11 telemetry fields
as the JSON output, plus three database-only columns:

| Column | Meaning |
| --- | --- |
| `id` | `INTEGER PRIMARY KEY AUTOINCREMENT` — a unique row number for this database. |
| `sent` | `0` = waiting to be transmitted, `1` = successfully transmitted. New rows start at `0`. |
| `sent_at` | Unix time in milliseconds when the row was marked sent; `NULL` until then. |

`sent`, `sent_at` and `id` are **never** added to the simulator's JSON output.
They exist only inside the database.

Two safeguards are built in:

- `UNIQUE (ts, node_id)` stops the same reading being stored twice. If a
  duplicate arrives, it is skipped instead of causing an error.
- An index on `(sent, ts)` makes finding unsent rows fast and returns them in
  timestamp order.

## MQTT + ThingsBoard integration

### Required environment variables

| Variable | Meaning |
| --- | --- |
| `THINGSBOARD_HOST` | Shared MQTT broker hostname for all three devices. Do **not** include `https://` or a port. Use `mqtt.thingsboard.cloud` for ThingsBoard Cloud (North America), `mqtt.eu.thingsboard.cloud` for Europe, or your own server's IP/domain. |
| `FSN_01_TOKEN` | Access token of the **FSN-01 Reservoir Outlet** device. |
| `FSN_02_TOKEN` | Access token of the **FSN-02 Community Tap** device. |
| `FSN_03_TOKEN` | Access token of the **FSN-03 Tanker Fill Point** device. |
| `THINGSBOARD_TOKEN` | *Legacy only.* One token for every node. Used **only** when none of the three `FSN_XX_TOKEN` variables are set. |

Each token is a password. Never put one in source code, screenshots or Git.

`demo.thingsboard.io` is a demo **web** account. It is **not** the ThingsBoard
Cloud MQTT broker, and port 8883 there is not reachable — using it produces
`timed out`. This is the most common configuration mistake.

### How to find your host and tokens

1. **Which server are you using?** If you logged in at `thingsboard.cloud`,
   your account is in the North America region and the MQTT host is
   `mqtt.thingsboard.cloud`. If you logged in at `eu.thingsboard.cloud`, use
   `mqtt.eu.thingsboard.cloud`. If you installed ThingsBoard yourself, use that
   machine's IP address or domain name instead.
2. **Get each token:** in the ThingsBoard web UI open **Devices → your device →
   Manage credentials** (or the device's **Check connectivity** dialog) and
   copy the **access token**. Repeat this for all three devices. Each token is
   a long random string. Never paste one into source code or a screenshot.
3. **Keep them together:** all tokens must belong to the same server/region as
   the host. A token from one region will not work in another.

Routing during `--sync`:

| Reading `node_id` | Token used | ThingsBoard device |
| --- | --- | --- |
| `FSN-01` | `FSN_01_TOKEN` | Reservoir Outlet |
| `FSN-02` | `FSN_02_TOKEN` | Community Tap |
| `FSN-03` | `FSN_03_TOKEN` | Tanker Fill Point |

Set the variables in your current terminal session:

Windows (PowerShell):

```powershell
$env:THINGSBOARD_HOST = "mqtt.thingsboard.cloud"
$env:FSN_01_TOKEN = "PASTE_FSN_01_DEVICE_TOKEN_HERE"
$env:FSN_02_TOKEN = "PASTE_FSN_02_DEVICE_TOKEN_HERE"
$env:FSN_03_TOKEN = "PASTE_FSN_03_DEVICE_TOKEN_HERE"
```

macOS / Linux:

```bash
export THINGSBOARD_HOST="mqtt.thingsboard.cloud"
export FSN_01_TOKEN="PASTE_FSN_01_DEVICE_TOKEN_HERE"
export FSN_02_TOKEN="PASTE_FSN_02_DEVICE_TOKEN_HERE"
export FSN_03_TOKEN="PASTE_FSN_03_DEVICE_TOKEN_HERE"
```

Quick check that the host is reachable from your machine (no token needed):

```powershell
Test-NetConnection mqtt.thingsboard.cloud -Port 8883
```

Alternatively, copy `.env.example` to `.env`, fill in your values, and the
program will load them automatically:

```powershell
Copy-Item .env.example .env
notepad .env
```

`.env` is ignored by Git. Never commit a real token. Variables already set in
the terminal take priority over the `.env` file, which is useful if several
group members share the machine. Values still starting with `replace-with-`
are ignored, so forgotten placeholders are reported as missing tokens instead
of being sent to the broker.

### What the MQTT code does

- Connects on port **8883** using **TLS with certificate verification enabled**.
  We never call Paho's insecure-mode function.
- Opens one TLS connection per configured node. Each gets a unique MQTT client
  ID so the broker does not disconnect an earlier node's session.
- Uses that device's access token as the MQTT **username** and an empty
  password.
- Publishes JSON to exactly `v1/devices/me/telemetry`.
- Uses **QoS 1** and waits for Paho's `wait_for_publish()` confirmation
  (the broker's PUBACK) before anything is marked sent.
- Sends the 11 telemetry fields in ThingsBoard's timestamp envelope: outer `ts`
  is the client acquisition time and `values` contains the same 11 fields,
  including `ts`. `id`, `sent` and `sent_at` stay in SQLite and never appear in
  the MQTT payload.
- If a node's token is missing, its rows stay pending and the log names the
  missing environment variable (never a token value). Other nodes still send.
- Logs only host, node ID, topic, timestamp and sync counts — never a token.

### Generate readings and synchronize

Two clear steps (recommended for a demo):

Windows (PowerShell):

```powershell
python -m src.main --scenario flood --count 30 --save-db
python -m src.main --sync
```

macOS / Linux:

```bash
python3 -m src.main --scenario flood --count 30 --save-db
python3 -m src.main --sync
```

Or do both in one command:

```powershell
python -m src.main --scenario flood --count 30 --save-db --sync
```

`--sync` on its own only syncs whatever is already pending. It is a **single
controlled attempt**, not an endless retry loop. If the broker is down, run
the same `--sync` command again later.

**Already-sent rows are safe.** The sync only queries `sent = 0`, so the 156
readings sent in Stage 3 are never read, resent, reset or modified.

### Test each device safely

Use three fresh readings — the simulator spreads them one per node:

```powershell
python -m src.main --scenario normal --count 3 --save-db
python -m src.main --sync
```

Then:

1. Watch the `[SYNC]` lines: each should show the node ID in brackets, e.g.
   `Marked id=1 ts=... (FSN-01) as sent.`
2. Check the local queue:

   ```powershell
   python -c "from src.database import initialize_database,count_readings,count_pending_readings; c=initialize_database(); print('stored:',count_readings(c),'pending:',count_pending_readings(c)); c.close()"
   ```

3. In ThingsBoard, open each device and confirm its **Latest telemetry** shows
   one new reading with the matching `node_id`.
4. To test the missing-token path on purpose, temporarily remove one
   `FSN_XX_TOKEN` from the terminal, generate one more reading and sync. The
   log should name the missing variable (for example `FSN_02_TOKEN`), never a
   token value, and that node's row should stay pending. Set the token again
   and re-run `--sync` — the row will then be delivered without regeneration.

### Pending versus sent readings

| `sent` value | Meaning |
| --- | --- |
| `0` | Stored locally, still waiting. It stays in the queue after a failed publish. |
| `1` | Confirmed delivered. `sent_at` holds the time of that confirmation. |

During an outage, readings keep accumulating with `sent = 0`. Nothing is
deleted. When connectivity returns, `--sync` reads pending rows oldest-first,
publishes them through the matching node's MQTT client, and marks each one sent
only after the broker confirms it. Because the payload uses the timestamp
envelope, replayed rows appear in ThingsBoard at their original client `ts`,
so the time-series chart backfills the gap correctly. If one publish fails, the
sync stops so the broker is not hammered; that row and all later rows remain
pending for the next run. If a node has no token configured, only that node's
rows are skipped and stay pending — the other nodes still send.

Check the counts with:

```powershell
python -c "from src.database import initialize_database,count_readings,count_pending_readings; c=initialize_database(); print('stored:',count_readings(c),'pending:',count_pending_readings(c)); c.close()"
```

### What is tested with mocks, and what needs a real connection

## ThingsBoard dashboard, states and alarms (Stage 4)

The Stage 4 files are under [`thingsboard/`](thingsboard/README.md). The
rule-chain JSON is a sanitised real export from a verified ThingsBoard 4.4.1
tenant. The dashboard was rebased from the user-supplied earlier export and
polished locally into a light municipal operations view with a 50/50 top split:
four colour-filled, non-clickable state-count cards on the left and three
non-clickable alarm bars on the right. Needs attention keeps its exported filter,
the node state badge is compact, metadata uses real fields plus a verified
demo-coordinate district mapping (FSN-01/FSN-02 Kathmandu, FSN-03 Lalitpur), and
both charts and alarm tables follow the selected device.
The verified tenant had three devices on the `FloodSafe Node` profile, six Task
3 alarm rules, the linked operational-state rule chain, a three-marker map with
click-through to node detail, gauges/trends/state badge and alarms tables with
duration. The deterministic publisher produced all four states and the exact
alarm severities, then a final normal reading cleared them. Earlier normal and
flood `--save-db --sync` runs left 192 stored rows and 0 pending rows; a later
interrupted sync left 222 stored, 205 sent and 17 pending rows that can be
retried with `--sync`. An earlier dashboard was imported as a new dashboard in
the verified tenant, but the current local file must be imported and visually
re-verified before it is treated as live. See `docs/demo_runbook.md` for the
end-to-end demonstration commands. The built-in `response` scenario shows the
Intervention → contain → verify → resume workflow, and the optional Gmail
notification steps are in `thingsboard/email_notification_setup.md`.

In a different ThingsBoard account you still need to:

1. Create the `FloodSafe Node` device profile, assign `FSN-01`–`FSN-03` to it,
   configure the six exact Task 3 alarm rules, and agree an inactivity timeout
   with your group (the assignment gives no value).
2. Import and link `thingsboard/rule_chain_operational_state.json`, then approve
   or replace its **PROPOSED** state thresholds with your group's decision.
3. Import `thingsboard/dashboard_floodsafe.json` and check all widgets. If the
   import fails or a widget is blank, use `thingsboard/dashboard_build_sheet.md`.
4. Use `thingsboard/verification_checklist.md` to record remaining evidence.
   Captured screenshots are in `thingsboard/screenshots/`. Do not describe the
   configuration as live in another tenant until you have verified it there.

The simulator, SQLite buffer, MQTT implementation and 11-field telemetry schema
were not changed. `thingsboard/publish_test_reading.py` publishes one controlled
reading for deterministic alarm tests without touching SQLite.

## Notes for the team

- `ts` is the simulated acquisition time in Unix epoch milliseconds. Samples
  in one run are spaced by `sample_interval_ms` in `config/nodes.json`; the
  program does not sleep, so a run finishes immediately.
- Edit `config/nodes.json` to change node details or the allowed sensor
  ranges. Keep the field names unchanged — later stages (database, MQTT,
  ThingsBoard) will use the same contract.
