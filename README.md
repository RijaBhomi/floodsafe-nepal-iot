# FloodSafe Nepal — IoT Assignment 3

**Current stage: project skeleton, Python virtual sensor simulator, SQLite local buffer, and MQTT/ThingsBoard synchronization.**

FloodSafe Nepal is a post-flood water-quality monitoring and decision-support
prototype for the Internet of Things (ITS67404) Assignment 3. Python simulates
ESP32-style monitoring nodes that report five water indicators from three water
points in Kathmandu Valley.

> **Important limitation:** this is an academic prototype, not a laboratory
> water-safety certification system. The readings are generated by a model.
> The coordinates are demonstration coordinates, not verified deployment
> locations and not a claim that equipment is installed there.

## What is included today

- Project folder skeleton and documentation.
- `config/nodes.json` with exactly three simulated nodes and the simulation
  settings.
- A standard-library-only Python simulator with two scenarios: `normal` and
  `flood`.
- JSON Lines output on screen and, optionally, to a file in `output/`.
- A SQLite local buffer (`src/database.py`) that stores readings with
  `sent = 0` until they are transmitted.
- MQTT over TLS publishing to ThingsBoard (`src/mqtt_client.py`) and a one-shot
  synchronization manager (`src/sync_manager.py`).
- Automated tests for the database and for MQTT/sync using mocks in `tests/`.

## What is NOT included yet

ThingsBoard dashboards, alarm rules, device provisioning in code, and
performance measurement. You still create the device and copy its access token
manually in the ThingsBoard web UI. The sync command is a single controlled
run — there is no endless retry loop in this stage.

## Telemetry schema (summary)

Every printed line is one JSON object with exactly these keys:

`ts`, `node_id`, `water_point`, `latitude`, `longitude`, `ph`,
`turbidity_ntu`, `tds_ppm`, `water_temp_c`, `flow_lpm`, `scenario`

See [`docs/telemetry_spec.md`](docs/telemetry_spec.md) for the full contract.

## Running the simulator

`--count` is the number of readings to generate **in total**; they are spread
evenly across the three nodes in round-robin order, so each node receives
roughly `--count / 3` readings.

### Normal scenario

Windows (PowerShell):

```powershell
python -m src.main --scenario normal --count 12
```

macOS / Linux:

```bash
python3 -m src.main --scenario normal --count 12
```

### Flood scenario

Windows (PowerShell):

```powershell
python -m src.main --scenario flood --count 12
```

macOS / Linux:

```bash
python3 -m src.main --scenario flood --count 12
```

The flood scenario uses one shared contamination severity for all three nodes.
Severity rises quickly, holds at a peak, then washes out slowly. Turbidity,
pH, TDS and flow all respond to that same severity, so the readings describe
one related event instead of independent random numbers.

## SQLite local buffer

### What SQLite is doing in our project

SQLite is a small database built into Python (`sqlite3`), so no installation or
server is needed. It acts as the **local storage** for our virtual node. Every
reading generated with `--save-db` is written to `data/floodsafe.db` before any
future transmission attempt. This is the first half of *store-and-forward*:
**store now, forward later**.

The table is named `sensor_readings`. It stores the same 11 telemetry fields
as the JSON output, plus three database-only columns:

| Column | Meaning |
| --- | --- |
| `id` | `INTEGER PRIMARY KEY AUTOINCREMENT` — a unique row number for this database. |
| `sent` | `0` = waiting to be transmitted, `1` = successfully transmitted. New rows start at `0`. |
| `sent_at` | Unix time in milliseconds when the row was marked sent; `NULL` until then. |

`sent`, `sent_at` and `id` are **never** added to the simulator's JSON output.
They exist only inside the database.

Two safeguards are built in:

- `UNIQUE (ts, node_id)` stops the same reading being stored twice. If a
  duplicate arrives, it is skipped instead of causing an error.
- An index on `(sent, ts)` makes finding unsent rows fast and returns them in
  timestamp order.

## MQTT + ThingsBoard integration

### Required environment variables

| Variable | Meaning |
| --- | --- |
| `THINGSBOARD_HOST` | MQTT broker hostname only. Do **not** include `https://` or a port. Use `mqtt.thingsboard.cloud` for ThingsBoard Cloud (North America), `mqtt.eu.thingsboard.cloud` for Europe, or your own server's IP/domain. |
| `THINGSBOARD_TOKEN` | Access token of one ThingsBoard device. Treat it like a password. |

`demo.thingsboard.io` is a demo **web** account. It is **not** the ThingsBoard
Cloud MQTT broker, and port 8883 there is not reachable — using it produces
`timed out`. This is the most common configuration mistake.

### How to find your host and token

1. **Which server are you using?** If you logged in at `thingsboard.cloud`,
   your account is in the North America region and the MQTT host is
   `mqtt.thingsboard.cloud`. If you logged in at `eu.thingsboard.cloud`, use
   `mqtt.eu.thingsboard.cloud`. If you installed ThingsBoard yourself, use that
   machine's IP address or domain name instead.
2. **Get the token:** in the ThingsBoard web UI open **Devices → your device →
   Manage credentials** (or the device's **Check connectivity** dialog) and
   copy the **access token**. It is a long random string. Never paste it into
   source code or a screenshot.
3. **Keep them together:** the token must belong to the same server/region as
   the host. A token from one region will not work in another.

Create a device first if you have not already. Use the token of the device you
want to simulate (for example `FSN-01`). To send a different node, change the
token before syncing.

Set the variables in your current terminal session:

Windows (PowerShell):

```powershell
$env:THINGSBOARD_HOST = "mqtt.thingsboard.cloud"
$env:THINGSBOARD_TOKEN = "PASTE_DEVICE_ACCESS_TOKEN_HERE"
```

macOS / Linux:

```bash
export THINGSBOARD_HOST="mqtt.thingsboard.cloud"
export THINGSBOARD_TOKEN="PASTE_DEVICE_ACCESS_TOKEN_HERE"
```

Quick check that the host is reachable from your machine (no token needed):

```powershell
Test-NetConnection mqtt.thingsboard.cloud -Port 8883
```

Alternatively, copy `.env.example` to `.env`, fill in your values, and the
program will load them automatically:

```powershell
Copy-Item .env.example .env
notepad .env
```

`.env` is ignored by Git. Never commit a real token. Variables already set in
the terminal take priority over the `.env` file, which is useful if several
group members share the machine.

### What the MQTT code does

- Connects on port **8883** using **TLS with certificate verification enabled**.
  We never call Paho's insecure-mode function.
- Uses the device access token as the MQTT **username** and an empty password.
- Publishes JSON to exactly `v1/devices/me/telemetry`.
- Uses **QoS 1** and waits for Paho's `wait_for_publish()` confirmation
  (the broker's PUBACK) before anything is marked sent.
- Sends only the 11 telemetry fields. `id`, `sent` and `sent_at` stay in
  SQLite and never appear in the MQTT payload.
- Logs only host, topic, timestamp and node ID — never the token.

### Generate readings and synchronize

Two clear steps (recommended for a demo):

Windows (PowerShell):

```powershell
python -m src.main --scenario flood --count 30 --save-db
python -m src.main --sync
```

macOS / Linux:

```bash
python3 -m src.main --scenario flood --count 30 --save-db
python3 -m src.main --sync
```

Or do both in one command:

```powershell
python -m src.main --scenario flood --count 30 --save-db --sync
```

`--sync` on its own only syncs whatever is already pending. It is a **single
controlled attempt**, not an endless retry loop. If the broker is down, run
the same `--sync` command again later.

### Pending versus sent readings

| `sent` value | Meaning |
| --- | --- |
| `0` | Stored locally, still waiting. It stays in the queue after a failed publish. |
| `1` | Confirmed delivered. `sent_at` holds the time of that confirmation. |

During an outage, readings keep accumulating with `sent = 0`. Nothing is
deleted. When connectivity returns, `--sync` reads pending rows oldest-first,
publishes them, and marks each one sent only after the broker confirms it. If
one publish fails, the sync stops so the broker is not hammered; that row and
all later rows remain pending for the next run.

Check the counts with:

```powershell
python -c "from src.database import initialize_database,count_readings,count_pending_readings; c=initialize_database(); print('stored:',count_readings(c),'pending:',count_pending_readings(c)); c.close()"
```

### What is tested with mocks, and what needs a real connection

- **Tested automatically with mocks:** topic, QoS 1, JSON payload field list,
  delivery confirmation, marking sent after success, leaving rows pending
  after failure or connection error, retry behaviour, and timestamp ordering.
- **Requires a real ThingsBoard connection:** confirming that your host,
  token, TLS certificate and device are correct, and seeing data in the
  ThingsBoard device view. The unit tests deliberately do not do this.

### Run the tests

The database tests use a temporary SQLite file and the MQTT tests use mocks, so
`data/floodsafe.db` and any real ThingsBoard connection are never used. Run
all 26 tests from the project root:

Windows (PowerShell):

```powershell
python -m unittest discover -s tests -v
```

macOS / Linux:

```bash
python3 -m unittest discover -s tests -v
```

### Command-line options

| Option | Required | Meaning |
| --- | --- | --- |
| `--scenario {normal,flood}` | yes | Which sensor model to run. Invalid names are rejected with a clear error. |
| `--count N` | yes | Total number of readings; must be a whole number of at least 1. |
| `--output PATH` | no | Write the same JSON lines to a file (for example `output/flood.jsonl`). |
| `--save-db` | no | Also store the readings in `data/floodsafe.db` with `sent = 0`. |
| `--sync` | no | Publish pending rows to ThingsBoard once, then exit. Alone: sync only. With generation: requires `--save-db`. |

## Notes for the team

- `ts` is the simulated acquisition time in Unix epoch milliseconds. Samples
  in one run are spaced by `sample_interval_ms` in `config/nodes.json`; the
  program does not sleep, so a run finishes immediately.
- Edit `config/nodes.json` to change node details or the allowed sensor
  ranges. Keep the field names unchanged — later stages (database, MQTT,
  ThingsBoard) will use the same contract.
